Routing rule of thumb

  • Junior engineer answers in <2 min, no deep context → Haiku 4.5
  • Needs real reasoning, multi-file context, stakes recoverable → Sonnet 5.5
  • Mistake is expensive, or a long agent run needs to hold its reasoning together → Opus 5.5
  • Hardest long-horizon reasoning, multi-repo agentic coding → Fable 5.1

Cost multipliers to watch

  • Output tokens cost 5× input on every current model ($1/$5, $2/$10, $4/$20, $10/$50) — response length is the line item to control hardest
  • Repeated large context sent fresh every call is the single biggest avoidable cost — cache it, but only where the same prefix gets reused several times
  • Real-time/interactive is priced for latency — batch async work is ~50% cheaper
  • Pinning inference to US-only (inference_geo) costs 1.1× on everything — input, output, cache writes and cache reads. Worth knowing before data-residency is set as a default. The same 1.1× applies on Claude Platform on AWS and to Foundry’s US Data Zone Standard deployments; Bedrock and Google Cloud regional and multi-region endpoints carry a separate 10% premium over global endpoints
  • ⚠ Delete carried-over verification instructions. Opus 5 verifies its own work unprompted, so prompts still saying “include a final verification step” or “use a subagent to verify” cause over-verification — tokens spent on work the model already did. Check your CLAUDE.md and skill bodies for these, and check Anthropic’s Opus 5.5 prompting guide for whether the behaviour carries over
  • Opus 4.7 and every model after it (including Sonnet 5 and 5.5, Opus 5 and 5.5, Fable 5 and 5.1) use a newer tokenizer. Anthropic puts the increase at approximately 30% more tokens for the same text, with the exact figure depending on content. Re-baseline any budget, max_tokens limit or token count carried over from Sonnet 4.6 or Opus 4.6 — and note the 1M window holds correspondingly less text
  • ⚠ Thinking tokens bill at the output rate, and on Opus 5.5 and Fable 5.1 adaptive thinking is always on — a request that disables it returns a 400. Since max_tokens is a hard cap on thinking plus response text, set it generously at the higher effort levels. Opus 5.5 defaults to medium effort, one level below Opus 5’s high, so a request that omits effort runs lighter than it did on Opus 5. Anthropic’s advice is to run an effort sweep on your own evals rather than carry settings over — measure your own before/after instead of trusting a headline multiplier
  • ⚠ Sonnet pricing check: Sonnet 5 launched at an introductory $2/$10 per MTok with $3/$15 announced as the standard rate from September 1. As of October 6, Anthropic’s pricing page lists both Sonnet 5 and Sonnet 5.5 at $2/$10 with no end date, so that step-up is not reflected there — confirm with your Anthropic account team before locking budgets. Separately, the newer tokenizer produces approximately 30% more tokens than Sonnet 4.6 for the same text, depending on content. If that holds on your workload, $2/$10 against Sonnet 4.6’s $3/$15 nets out to roughly 13% cheaper per equivalent request (⅔ × 1.3 ≈ 0.87) — an estimate, so measure your own traffic.

Which surface to use

  • Claude Code in VS Code / JetBrains — fast, single-function fixes with inline diffs. Low per call but watch frequency
  • Claude Code CLI / agent mode — multi-file edits, autonomous runs. Scope tightly — unscoped agents burn tokens fast. Same engine and same .claude/ config as the IDE extensions
  • Claude.ai / web chat — docs, ADRs, brainstorming, non-code writing. No repo context overhead
  • Batch API — bulk test gen, nightly summaries, log triage. Anything with no human waiting on it

Biggest sources of avoidable token spend — context strategy & model routing

1. Summary layer for large files

  • For any reference file over ~100 lines, create a companion summary (~20–50 lines)
  • Load summary by default. Load full file only when authoring that specific section
  • Applies to: architecture docs, plans, contract bundles, runbooks
  • Directional estimate: most of that file's input cost, per command. Unmeasured — worth instrumenting on your own repos

2. Scoped state/memory loading

  • Tag each task with the module it touches
  • Load only state files for that module — not all state files in the project
  • 6-module project, task touches 1 → load one sixth of the state files
  • Saving scales with module count, assuming modules are roughly comparable in size — skewed repos save less

3. Prompt caching for static context

  • Static content first in fixed order (tools → system → messages); variable content — the specific task, the target file — goes last, after the breakpoint
  • Hits require 100% identical prompt segments up to the breakpoint. A change invalidates from that point forward along the tools → system → messages hierarchy — not necessarily the whole cache, since with several breakpoints an earlier prefix can still hit
  • Writes cost 1.25× base input (5-minute) or 2× (1-hour). Reads cost 0.1× on Haiku 4.5, Sonnet 5.5 and Sonnet 5 — but 0.05× on Opus 5.5 and 0.025× on Fable 5.1. Cache hits per MTok: $0.10 Haiku 4.5, $0.20 Sonnet 5.5, $0.20 Opus 5.5, $0.25 Fable 5.1 (Opus 5 is $0.50 and Fable 5 is $1)
  • ⚠ The minimum cacheable prefix is per-model and runs opposite to what you'd guess: 512 tokens on Opus 5.5, Sonnet 5.5 and Fable 5.1 (also Opus 5 and Fable 5), 1,024 on Sonnet 5 and Sonnet 4.6, but 4,096 on Haiku 4.5. Below the floor nothing caches and no error is returned — so short conventions files cache fine on the 5.x models and silently don't on Haiku
  • ⚠ Changing top-level effort or speed mid-session invalidates cached prefixes, because both are rendered into the prompt. Setting effort explicitly to the model’s default is the same as omitting it and does not invalidate. New: on Fable 5.1, Opus 5.5, Opus 5 and Sonnet 5.5, a per-message effort change (beta, header mid-conversation-output-config-2026-07-01) keeps the cache intact. Elsewhere, Anthropic’s guidance stands: pick an effort level at the start of a session and keep it constant, varying it across workloads instead
  • The 5-minute TTL runs from the start of the request, not the end of the response, and refreshes free on every hit. A 4-minute Opus 5.5 response leaves only ~1 minute to land the next call
  • Saving applies to cached input only — output is untouched. On that portion, with 5-minute writes: at the standard 0.1× read rate ~32% at 2 calls, ~52% at 3, ~78% at 10; on Opus 5.5 (0.05×) ~35% / ~55% / ~83%; on Fable 5.1 (0.025×) ~36% / ~57% / ~85%. The "90%" headline needs ~100 reads of the same prefix

4. Edit artifacts, don't re-run

  • For small changes to spec/plan/task files — edit the artifact directly
  • Reserve full re-runs for genuine scope changes affecting majority of the document
  • Run analysis at deliberate gates (end of phase, pre-PR) not after every edit
  • Estimated saving: several thousand tokens per avoided re-run, scaling with artifact size

5. Route the model per command — don't run a whole workflow on one tier

  • Every SDD command is a different work type. Running them all on one session default means you either overpay for the cheap steps or under-serve the expensive ones — and the cheap steps are the frequent ones
  • Declare the tier once, in the command itself — model: and effort: in each skill's frontmatter. It then applies automatically for that turn and reverts after, so routing survives the person who set it up
  • Pin the project baseline in .claude/settings.json so anything unrouted lands on the workhorse rather than inheriting whatever tier the last session used
  • effort: is the half of this lever most teams ignore. The ladder is low · medium · high · xhigh · max. The API defaults to high on every model except Opus 5.5, which defaults to medium — so unless you set it, Sonnet 5.5 and Fable 5.1 run on high, the middle of five rungs with xhigh and max above it. Setting the default explicitly is identical to omitting it
  • It moves more than thinking: effort affects all response tokens, including how many tool calls Claude makes. That is why it bites hardest on agentic runs
  • It is a tradeoff, not free money — lower effort buys speed and cost while accepting some reduction in capability. Anthropic’s calibration point for Sonnet 5 was that medium is comparable to Sonnet 4.6 at high. Sonnet 5.5’s levels are recalibrated, so re-run the sweep rather than carrying that over — for agentic coding Anthropic suggests starting at medium for well-specified tasks and high for harder or longer ones
  • ⚠ Anthropic documents that on Opus 5, effort controls thinking volume, not visible response length — if you want shorter output, ask for it in the prompt (test whether Opus 5.5 behaves the same). And Haiku 4.5 does not support effort at all, so it has no dial beyond the model choice itself
  • At standard rates Sonnet 5.5 is half the per-token price of Opus 5.5 ($2/$10 vs $4/$20), before any effort reduction — and 80% below Fable 5.1. Your actual saving depends on your phase mix and token counts, so instrument it rather than quoting this number

Within /speckit-implement — model per task, effort per run
  • ⚠ Read this before splitting effort per task. Changing the top-level effort value between requests invalidates cached prefixes, so vary it across workloads rather than within a run. On Sonnet 5.5, Opus 5.5, Opus 5 and Fable 5.1, per-message effort (beta) lets you change it mid-run without losing the cache — except on Sonnet 5.5 with between_tools, which can’t change effort mid-conversation. Switching model per task still forfeits the cache either way
  • Trivial (renames, config, doc updates, boilerplate with a precedent) → Sonnet 5.5. Batch these into their own low-effort run, or drop effort with a per-message change where the model supports it
  • Standard (a component, an endpoint, a test suite) → Sonnet 5.5 at the run's effort level — the default
  • Complex (auth/payments/safety-critical, named regression-risk areas, concurrency or ordering guarantees, novel algorithms) → Opus 5.5, high
  • Classify from the task's own text in tasks.md, not a guess. When unsure, stay put and re-read the acceptance criteria before escalating
  • De-escalate the model the moment the complex task's tests pass — a session parked on Opus 5.5 for the rest of the run is the whole saving gone
  • If a phase genuinely needs a different effort level, that is a signal to make it a separate run, which is what the routing table already does per command
The trap that cancels routing out
  • ⚠ Caches are model-scoped, so switching tier mid-session forfeits your cache hits and the remaining context is processed at the new model's rates. How much that costs depends on what gets sent and what still hits cache — but a cheap command run straight after an expensive one, in the same session, can erase the saving
  • House practice, not an Anthropic requirement: /clear between phases, so a cheap command's routing applies to a small context rather than the previous phase's transcript
  • Worst offender: a Sonnet 5.5 low-effort checklist run immediately after an Opus 5.5 plan, in the same session
  • Audit frontmatter against the routing table above after every retier — a table that has drifted from the skills it documents is routing nothing
  • General session discipline is in Tips & Tricks → Session & context management; the point here is only that per-command routing makes phase boundaries worth respecting

Debugging — avoid the instinct to paste everything

  • Give a hypothesis, not just symptoms — "looks like a race condition between X and Y" focuses reasoning and shortens the conversation
  • Paste the minimal reproducible snippet — not the surrounding file or unrelated imports
  • Ask for root-cause explanation plus fix in one prompt — not 'what's wrong' then separately 'now fix it'
  • For flaky bugs: summarize the failure pattern yourself (or have Haiku do it cheaply) before escalating to Sonnet 5.5/Opus 5.5

Documentation — low-reasoning, high-volume. Ideal for cheap tiers and batching.

  • Ask for output in the final target format (Markdown, OpenAPI) directly — avoid a second formatting pass
  • Batch doc-generation for an entire module or sprint's PRs in one Batch API job — not one interactive call per file

Day-to-day coding — highest frequency, small per-call savings compound the most

  • Ask for incremental diffs on existing files rather than full-file rewrites — this is the single highest-frequency chance to apply it

↓ Shrink input tokens

  • Share only the relevant function/class — not the whole file or repo
  • Strip comments, blank lines, and unrelated code from pasted snippets
  • Summarize long logs to relevant lines first (Haiku pre-pass is cheap)
  • Cache reused context (system prompts, style guides, schemas) — reads cost 0.1× input, but the first write costs 1.25×, so it only pays from the second reuse onward
  • Avoid re-sending full conversation history when a fresh focused prompt would do
  • Reference reusable context by name/link where the tool supports it

↑ Shrink output tokens

  • Ask for a diff or patch — not a full file rewrite when only part changes
  • Set explicit limits: "in 3 bullet points," "under 100 words," "return only the function"
  • Ask for code without inline prose when you only need the code
  • Request structured output (table, JSON, fixed template) — shorter than free-form prose
  • Step effort down for routine tasks — on Sonnet 5.5, Opus 5.5 and Fable 5.1 that is the control, since they use adaptive thinking (it can’t be switched off on Opus 5.5 or Fable 5.1; on Sonnet 5.5 between_tools is the lowest thinking setting)

📞 Reduce number of calls

  • Batch related asks into a single prompt ("review these 4 functions")
  • Front-load constraints so the first response is usable — avoid 2–3 correction follow-ups
  • Non-urgent high-volume work → Batch API (half the cost, no babysitting)
  • Don't make 'just checking' calls — trust and verify locally where possible

⚙ Model & tooling hygiene

  • Set Sonnet 5.5 as team default — Haiku/Opus 5.5/Fable 5.1 require conscious escalation
  • Audit usage dashboards regularly for model-routing drift toward expensive defaults
  • Keep tool/function schemas lean in agentic setups — every schema adds fixed overhead per call
  • Claude Code shares your editor selection and diagnostics with the session — run /context for a live breakdown of what is actually loaded, including which CLAUDE.md and memory files came in
  • Right-size context windows — don't load 200K+ tokens for a 50-line question

🕐 Session & context management

  • Stay in the same session for a continuous task — switching means re-explaining context
  • Don't keep one session running across unrelated tasks — every new message re-bills all prior history
  • For a multi-step task (implement → test → fix), keep it in one session
  • When session grows long and only recent exchanges matter, start fresh with a short recap
  • Avoid running the same task in parallel across multiple sessions 'to compare answers'
  • Don't switch models mid-task without reason — caches are model-scoped, so you forfeit cache hits and the remaining context is reprocessed at the new model's rates
  • Use built-in memory/project context features instead of re-pasting background info every session
✅ Checklist

Before every AI call

  • Cheapest tier that does the job correctly?
  • Full prompt built (goal + constraints + minimal context + output format)?
  • Context trimmed to what's relevant — no whole files or logs 'just in case'?
  • Asking for a diff/patch, not a full file rewrite?
  • Output format and length specified up front?
  • Agent mode only if the task genuinely needs multi-file autonomy?
  • Could this wait? Non-urgent bulk work belongs on the Batch API, not an interactive call
